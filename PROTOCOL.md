# agentstatus protocol, version 1

## Purpose

A tiny file convention for publishing the live status of coding-agent sessions:
which session is working, which one needs a human, which one is idle. Every
agent writes one small JSON file per session into a shared directory; any
number of readers (a panel, a status bar, a script) read that directory. There
is no daemon, no socket and no network. An agent can be integrated with one
line of shell, without reading any agentstatus code.

The machine-readable schema is [`schema/session.v1.json`](schema/session.v1.json).

## Location

Sessions live in `$AGENTSTATUS_DIR` if set, otherwise:

- macOS, Linux: `~/.agentstatus/sessions/`
- Windows: `%LOCALAPPDATA%\agentstatus\sessions\`

Each session is one file named `<agent>@<id>.json`. `agent` and `id` consist
only of `[A-Za-z0-9._-]`, 1 to 128 characters, and are never `.` or `..`.
Because `-` is allowed inside both names, `@` separates them; the file name is
therefore unambiguous and safe. Writers must reject other characters. Readers
must not trust the file name and take `agent` and `id` from the file content.

## Fields

```json
{
  "v": 1,
  "agent": "claude-code",
  "id": "3f2b9c1e-0000-4000-8000-000000000001",
  "status": "waiting",
  "cwd": "/Users/me/src/myproject",
  "title": "Polish milestone 5",
  "pid": 18667,
  "since": "2026-10-06T18:40:12Z",
  "updated": "2026-10-06T18:41:03Z",
  "detail": "Claude needs your permission to use Bash"
}
```

| Field | Required | Meaning |
|---|---|---|
| `v` | yes | Protocol version, integer. Readers ignore files with an unknown major version. |
| `agent` | yes | Short name of the agent (`claude-code`, `codex`, `grok`, `gemini-cli`, free to choose) |
| `id` | yes | The agent's session id, otherwise freely assigned |
| `status` | yes | `working`, `waiting`, `idle` or `error` |
| `updated` | yes | Last change, RFC 3339 UTC |
| `since` | no | Since when the current `status` holds; if absent, `updated` applies |
| `cwd` | no | Working directory, absolute path |
| `title` | no | Human-readable session name; if absent, a UI shows the name of the project root (nearest folder upward from `cwd` containing `.git`, else the directory name) |
| `topic` | no | Short topic of the session, generated by the agent itself; UIs show it as a second line under the name. At most 120 characters; an empty value keeps the old one |
| `pid` | no | Process the session hangs on (used for cleanup); integer, at least 1 and at most 2147483647 |
| `detail` | no | One sentence on why the state holds (mostly for `waiting` / `error`), at most 200 characters |

Unknown fields are allowed and ignored, so the format can be extended without a
new major version.

## States

- `working`: the agent is working right now.
- `waiting`: the agent needs the human (approval, a question).
- `idle`: finished, ready for the next task.
- `error`: aborted or failed.
- **Ended** is not a state: the file is gone.

## Writing

- Write atomically: write `<name>.json.tmp-<pid>` in the same directory, then
  `rename` it over `<name>.json`. A reader never sees a half-written file.
  Temporary files do not end in `.json`, so readers skip them.
- Set `since` only when `status` changes; otherwise keep the old value. Always
  refresh `updated`.
- `detail` describes the current state only: it is replaced on every write, and
  omitted means cleared. At most 200 characters.
- Strip control characters from `title`, `topic`, `detail` and `cwd`: newline, carriage
  return and tab become a space, all others are removed. These strings often
  originate from prompts or tool output.
- When the session ends, remove the file.
- If the process the session hangs on is known, record it in `pid`. It must be
  the long-lived agent process, not a short-lived helper (such as the shell a
  hook runs in): a dead `pid` marks the session as ended.

## Reading and cleanup

- A file that does not parse, has an unknown `v`, an invalid `agent`/`id`/`status`
  or lacks a required field is skipped: do not delete it, do not crash.
- `pid` set and no such process exists: the session has ended; the reader may
  delete the file. A `pid` outside 1 to 2147483647 makes the file invalid (skip it).
- `pid` set and `updated` earlier than the last system boot: the session has
  ended (the machine restarted or crashed, and the pid may belong to another
  process now); the reader may delete the file. Skip this rule if the boot time
  is unknown.
- No `pid`: `updated` older than 24 hours marks the session **stale** (show it
  greyed out); older than 7 days, delete it.
- Sort order for UIs: `waiting`, `working`, `error`, `idle`, stale; within the
  same rank by `since`, oldest first.
- Sanitize before printing to a terminal: other writers may not have stripped
  control characters (escape sequences in `title`, `detail`, `cwd`).

## Minimal writer in shell

```sh
dir="${AGENTSTATUS_DIR:-$HOME/.agentstatus/sessions}"; (umask 077; mkdir -p "$dir")
now=$(date -u +%Y-%m-%dT%H:%M:%SZ)
printf '{"v":1,"agent":"my-agent","id":"%s","status":"working","updated":"%s"}' "$ID" "$now" > "$dir/my-agent@$ID.json.tmp-$$"
mv "$dir/my-agent@$ID.json.tmp-$$" "$dir/my-agent@$ID.json"
```

Remove `"$dir/my-agent@$ID.json"` when the session ends.

## Adapters

| Agent | Mechanism | Status |
|---|---|---|
| Claude Code | Hooks in `settings.json`, installed by `agentstatus install claude` | available |
| Grok | Claude hook, by compatibility (Grok reads `~/.claude/settings.json`) | available, per docs; still to be confirmed on a real run. Detection is by process name, the environment (`GROK_SESSION_ID`) only as fallback |
| Codex | Hooks in `~/.codex/hooks.json` (or `$CODEX_HOME`), installed by `agentstatus install codex` | per docs; still to be confirmed on a real run. Codex asks you to trust the hook once (`/hooks`) |
| Grok (native) | Own hook file `~/.grok/hooks/agentstatus.json`, installed by `agentstatus install grok` | experimental: native hooks not yet verified on a real run; Grok also runs the Claude hooks via its compatibility layer, and also reports `StopCancelled`, `StopFailure`, `PermissionDenied` |
| Gemini CLI | Hooks in `settings.json` | planned |
| anything else | `agentstatus run -- <cli>` | available |

### Claude Code

`agentstatus hook claude` reads the hook event from stdin and maps it:

| Hook event | Result |
|---|---|
| `SessionStart`, `StopCancelled` | `idle` (`SessionStart` with source `compact` is ignored) |
| `Stop` | `idle`, or `waiting` (detail `Claude asked you something`) when the last answer ends with a question mark (a heuristic: markdown characters and closing parentheses at the end are ignored; the answer comes from the payload's `last_assistant_message` or the end of the transcript) |
| `PreToolUse` of the tools `AskUserQuestion`, `ExitPlanMode` only (installed with a matcher) | `waiting`; the dialog fires neither `Notification` nor `Stop`, `PostToolUse` after the answer sets `working` again |
| `UserPromptSubmit`, `PostToolUse`, `PermissionDenied` | `working` |
| `StopFailure` | `error`, the error type as `detail` |
| `Notification` of type `permission_prompt`, `elicitation_dialog`, `elicitation_url_dialog`, `agent_needs_input` (or no type) | `waiting`, the message as `detail` |
| `Notification` of type `idle_prompt`, `task_complete` | `idle` |
| `SessionEnd` | file removed |

The bundled adapters set no `title`; UIs show the project root name instead (nearest folder with `.git`).
`pid` is the agent process above the hook's shell. An agent that runs its hooks from a shared background service (parent pid 1, as Codex does) writes no `pid`, since the service outlives the session; such sessions age through `updated` (stale after 24 hours, then deleted).
Unknown events are ignored, and a failing hook exits 0 so it never disturbs the
agent.

### Grok

Grok reads Claude's hooks, so `agentstatus hook claude` also sees Grok sessions and writes
`agent: grok` when the agent process name starts with `grok` (a name starting with `claude` stays
`claude-code`); only when the name is empty or ambiguous (e.g. `node`) does `GROK_SESSION_ID` decide. The
payload's camelCase `sessionId` and snake_case `hookEventName` (e.g. `stop_cancelled`) are accepted
next to Claude's fields and map to the same events. Based on Grok's documentation; still to be
confirmed on a real run.

`StopCancelled`, `StopFailure` and `PermissionDenied` are Grok/Claude-side events that
`agentstatus install claude` deliberately does not register (unknown keys might disturb Claude's
settings check); they arrive only with a dedicated Grok install. Until then Esc in Grok heals via the
`idle_prompt` notification, a little later.

`agentstatus install claude` adds the hooks additively to
`~/.claude/settings.json` (or `$CLAUDE_CONFIG_DIR`), follows symlinks, writes a
uniquely named backup, shows the diff and asks. `agentstatus uninstall claude`
removes exactly those entries.

### Codex

`agentstatus hook codex` maps (Codex hook docs, `agent: codex`):

| Hook event | Result |
|---|---|
| `SessionStart` (source `compact` is ignored), `Stop`, `Interrupt` | `idle` |
| `UserPromptSubmit`, `PostToolUse` | `working` |
| `PermissionRequest` | `waiting`, `tool_input.description` (else the tool name) as `detail` |
| `SessionEnd` | file removed |

After a denied approval the session stays `waiting` until `Stop` or `Interrupt`. `tool_input` may be
any JSON value; `description` is used only if it is an object with a string `description`.
Codex runs hooks from a background service, so `agentstatus hook codex` writes no `pid`; a codex session ends when `SessionEnd` arrives or its `updated` ages out.

`agentstatus install codex` adds the hooks additively to `~/.codex/hooks.json`
(or `$CODEX_HOME/hooks.json`) with the same safeguards as for Claude. It refuses if Codex is not
found (no `~/.codex` / `$CODEX_HOME` and no `codex` in `PATH`). Codex
requires non-managed hooks to be trusted once: open a Codex session and
confirm the new hook in `/hooks`. Fixtures are written from the documentation,
not recorded from a real run.

### Any other CLI

`agentstatus run [--agent A] [--id I] [--title T] -- <command> [args...]`
reports `working` with the child's pid while it runs, removes the file when it
exits, and returns the child's exit code (128 + signal if it was killed).
Ctrl-C reaches the child. It knows only "running" and "ended".
